# Пошаговый план развития мониторинга auditd

Этот roadmap дополняет документ:

```text
docs/audit-monitoring-proposal.md
```

Цель — постепенно добавить в шаблон мониторинг security-событий auditd, не
внося больших изменений за одну итерацию. Каждый новый механизм сначала должен
быть понятен, проверен на тестовом компьютере и только после этого расширен.

## Правило работы над каждой итерацией

Каждый шаг выполняется отдельно по одному и тому же циклу:

1. Обсудить назначение изменения и ожидаемый результат.
2. Показать предлагаемые item key, регулярное выражение и trigger expression.
3. Получить явное согласование изменения.
4. Изменить минимально необходимую часть шаблона.
5. Проверить YAML, UUIDv4, уникальность UUID и item keys.
6. Импортировать шаблон в тестовый Zabbix.
7. Проверить состояние item в Latest data и отсутствие `NOTSUPPORTED`.
8. Создать контролируемое тестовое событие, если это безопасно.
9. Оценить количество и содержание полученных данных.
10. Зафиксировать результат в документации.
11. Создать отдельный коммит только для этой итерации.
12. Перейти к следующему шагу только после согласования.

Если проверка неуспешна, следующая функциональность не добавляется. Сначала
исправляется или откатывается текущая итерация.

## Ограничение размера изменений

Одна итерация должна содержать только один из следующих вариантов:

- один новый item без триггера;
- один триггер и необходимые ему макросы;
- одно уточнение регулярного выражения;
- одно изменение тегов или документации;
- один новый PARSEC-фильтр;
- один небольшой технический тест или валидатор.

Не следует в одном коммите одновременно добавлять несколько категорий auditd,
несколько триггеров и перерабатывать структуру шаблонов.

## Этап 0. Подготовка без изменения шаблона

### Шаг 0.1. Определить расположение и ротацию журнала

На тестовом компьютере нужно подтвердить:

```text
/var/log/audit/audit.log
```

Также нужно получить фактические имена ротированных файлов, например:

```text
audit.log.1
audit.log.2
```

Результат шага — точное регулярное выражение пути для `logrt[]` и
`logrt.count[]`.

Промежуточный результат проверки на тестовом компьютере:

```text
log_file = /var/log/audit/audit.log
max_log_file = 8
num_logs = 5
max_log_file_action = ROTATE
```

Обнаруженные файлы:

```text
audit.log
audit.log.1
audit.log.2
audit.log.3
audit.log.4
```

Для item key принято выражение, допускающее основной файл и числовые ротации:

```regex
/var/log/audit/^audit\.log(\.[0-9]+)?$
```

Статус: выполнено 2026-08-11.

Изменение шаблона: отсутствует.

### Шаг 0.2. Проверить доступ агента

Нужно определить, может ли пользователь процесса `zabbix-agent2` читать каталог
и файл журнала. Проверяются одновременно обычные Unix-права и ограничения
Astra Linux SE.

Возможные результаты:

1. Агент уже читает журнал — можно переходить к первому item.
2. Нужен ограниченный read-доступ с учетом ротации.
3. Прямой доступ нежелателен — выбранные события нужно выводить в отдельный
   файл.

Результат проверки на тестовом компьютере:

```text
zabbix-agent2 отображается с основной группой zabbix
/var/log/audit принадлежит root:adm и имеет режим 0750
проверка открытия файла от имени zabbix не была выполнена из-за запрета PAM
учетная запись zabbix входит в дополнительную группу adm с GID 4
запущенный процесс zabbix_agent2 имеет дополнительные группы 4 и 123
/var/log/audit/audit.log принадлежит root:adm и имеет режим 0640
```

`ps` показывает только основную группу процесса. Дополнительное членство в `adm`
или отдельный ACL могут предоставлять агенту доступ к журналу. `namei` был
запущен от интерактивного пользователя и поэтому также не доказывает отсутствие
доступа именно у процесса агента.

Членство в `adm` объясняет, каким образом предустановленные log items могут
читать журнал без изменения XML-шаблона: доступ предоставляется на стороне ОС,
а не самим шаблоном.

Статус: выполнено 2026-08-11. На уровне Unix DAC процесс агента может пройти
каталог и прочитать файл через дополнительную группу `adm`. Права не изменялись.
Фактическое чтение и возможные ограничения мандатной политики будут окончательно
проверены первым `logrt.count[]` item на шаге 1.1.

Изменение шаблона: отсутствует.

### Шаг 0.3. Собрать обезличенные примеры событий

Этот шаг выполняется постепенно. Сначала собирается только пример неудачной
аутентификации, необходимый для шага 1.1. Остальные категории исследуются перед
добавлением соответствующих items, а не все одновременно.

Нужны примеры реальных строк следующих категорий:

```text
USER_AUTH
USER_LOGIN
CONFIG_CHANGE
DAEMON_ERR или DAEMON_ABORT
ADD_USER или USER_MGMT
AVC или USER_AVC
parsec-f
parsec-p
```

Имена пользователей, адреса, пути и команды перед передачей примеров нужно
обезличить. Примеры используются только для проверки регулярных выражений.

Для первой итерации получена запись следующей структуры (значения окружения
обезличены):

```text
type=USER_AUTH msg=audit(<timestamp>:<serial>): pid=<pid> uid=0 auid=4294967295 ses=4294967295 subj=<label> msg='op=PAM:authentication grantors=? acct="<redacted>" exe="<redacted>" hostname=<redacted> addr=? terminal=<redacted> res=failed'
```

Подтверждено:

- тип записи — `USER_AUTH`;
- операция — `PAM:authentication`;
- неуспешный результат находится в той же строке как `res=failed`;
- предложенный фильтр `type=(USER_AUTH|USER_LOGIN).*res=failed` соответствует
  реальному формату;
- `auid=4294967295` и `ses=4294967295` означают, что login UID и audit-сессия
  еще не назначены, что ожидаемо для неуспешной попытки входа через дисплейный
  менеджер.

Статус: минимальная цель шага выполнена 2026-08-12. Примеры других категорий
будут собираться непосредственно перед соответствующими items, чтобы не
исследовать и не менять несколько направлений одновременно.

Изменение шаблона: отсутствует.

### Шаг 0.4. Согласовать структуру шаблонов

До первой реализации нужно выбрать один из вариантов:

1. Временно добавлять audit items в `Template Astra Linux Basic`.
2. Сразу создать отдельный `Template Astra Linux Audit`.

Предпочтителен второй вариант: базовые проверки состояния ОС остаются отдельно
от потока security-событий. PARSEC в дальнейшем также можно вынести в
`Template Astra Linux PARSEC`.

Принятое решение:

```text
Template Astra Linux Audit
```

Шаблон создается отдельным YAML-файлом. `Template Astra Linux Basic` не
изменяется. PARSEC в первую итерацию не входит и позднее будет рассматриваться
как отдельный компонент.

Статус: выполнено 2026-08-12.

## Этап 1. Первый работающий audit item

### Шаг 1.1. Добавить счетчик неудачной аутентификации

Добавляется только один активный item без триггера:

```text
Audit: failed authentication events count
```

Предлагаемый фильтр:

```regex
type=(USER_AUTH|USER_LOGIN).*res=failed
```

Предлагаемый тип ключа:

```text
logrt.count[]
```

Реализованный ключ:

```text
logrt.count["/var/log/audit/^audit\.log(\.[0-9]+)?$","type=(USER_AUTH|USER_LOGIN).*res=failed","UTF-8",1000,skip]
```

Параметры item:

```text
type: ZABBIX_ACTIVE
delay: 30s
history: 30d
trends: 365d
value_type: UNSIGNED
```

Результат проверки:

```text
шаблон успешно импортирован
item находится в состоянии supported
значения поступают в Latest data
контролируемая ошибка входа ожидаемо увеличивает счетчик
```

Статус: выполнено 2026-08-12. Триггеры на этом шаге не добавлялись.

Назначение шага:

- проверить чтение audit.log агентом;
- проверить работу ротации;
- понять семантику `logrt.count[]`;
- увидеть, какое число возвращается за один интервал;
- не создавать Problems до подтверждения качества данных.

Проверка:

1. Item находится в состоянии supported.
2. В Latest data регулярно поступают числовые значения.
3. Контролируемая неудачная аутентификация увеличивает счетчик.
4. При обычной работе нет неожиданно большого потока событий.

Отдельный коммит:

```text
Add failed authentication audit counter
```

### Шаг 1.2. Добавить WARNING-триггер

После наблюдения за item добавляются:

- макрос порога;
- макрос временного окна, если выражение Zabbix допускает выбранную форму;
- один trigger severity `WARNING`.

Начальный ориентир:

```text
5 событий за 5 минут
```

Точные значения согласовываются по фактическим данным. На этом шаге не
добавляется `HIGH`-триггер.

Проверка:

1. Единичная ошибка не создает лишнюю проблему, если это согласованное поведение.
2. Серия контролируемых ошибок активирует trigger.
3. Trigger автоматически восстанавливается после окончания временного окна.

Отдельный коммит:

```text
Alert on repeated authentication failures
```

### Шаг 1.3. Добавить HIGH-триггер

После проверки `WARNING` добавляется отдельный порог, например:

```text
20 событий за 5 минут
```

Нужно настроить зависимость так, чтобы при `HIGH` не создавалась лишняя
одновременная проблема `WARNING`.

Отдельный коммит:

```text
Escalate excessive authentication failures
```

## Этап 2. Работоспособность самого аудита

### Шаг 2.1. Добавить счетчик ошибок auditd

Добавляется один item без триггера.

Фильтр-кандидат:

```regex
type=(DAEMON_ABORT|DAEMON_ERR)
```

Цель — увидеть критические ошибки подсистемы аудита, которые не определяются
проверкой `auditd.service=active`.

Важно: работающая служба и исправная запись аудита — разные состояния.

Отдельный коммит:

```text
Collect audit daemon errors
```

### Шаг 2.2. Добавить HIGH-триггер ошибок auditd

После подтверждения фильтра добавляется один trigger: любое новое совпадение
считается критичным.

На этом шаге отдельно изучается, как trigger по счетчику возвращается в OK и как
не потерять повторные события в пределах одного открытого Problem.

Отдельный коммит:

```text
Alert on audit daemon errors
```

## Этап 3. Изменения конфигурации безопасности

### Шаг 3.1. Добавить item изменений конфигурации

Фильтр-кандидат:

```regex
type=(USYS_CONFIG|DAEMON_CONFIG|CONFIG_CHANGE|MAC_CONFIG_CHANGE|USER_MAC_CONFIG_CHANGE)
```

Сначала добавляется только счетчик. Нужно выяснить, какие штатные операции Astra
Linux создают эти записи и насколько они часты.

Отдельный коммит:

```text

```

### Шаг 3.2. Добавить WARNING-триггер

Любое подтвержденное изменение конфигурации создает аудиторское событие
severity `WARNING` или `INFO`. Severity согласовывается после просмотра реальных
строк.

На этом шаге решается, требуется ли `manual_close`.

Отдельный коммит:

```text
Alert on audit configuration changes
```

## Этап 4. Управление пользователями и группами

### Шаг 4.1. Добавить счетчик изменений учетных записей

Фильтр-кандидат:

```regex
type=(ADD_USER|DEL_USER|ADD_GROUP|DEL_GROUP|USER_CHAUTHTOK|USER_MGMT|GRP_MGMT|ROLE_ASSIGN|ROLE_REMOVE)
```

Сначала проверяется, какие типы действительно создаются в Astra Linux 1.8 и не
дублируют ли несколько строк одно логическое событие.

Отдельный коммит:

```text
Collect account management audit events
```

### Шаг 4.2. Добавить информационный триггер

Любое изменение учетной записи или группы фиксируется как аудит-событие. На
первой итерации рекомендуется severity `INFO` и ручное закрытие.

После эксплуатации можно отдельно обсудить повышение severity для удаления
пользователя, смены пароля или назначения роли.

Отдельный коммит:

```text
Report account management changes
```

## Этап 5. Аномалии и целостность

### Шаг 5.1. Добавить счетчик аномалий

Фильтр-кандидат:

```regex
type=(ANOM_[A-Z_]+|INTEGRITY_[A-Z_]+)
```

Сначала item работает без trigger. Проверяется реальный набор типов, потому что
предустановленный шаблон перечисляет типы, которые его исходный фильтр не ловит.

Отдельный коммит:

```text
Collect audit anomaly events
```

### Шаг 5.2. Добавить HIGH-триггер

После подтверждения отсутствия штатного шума любое событие этой категории может
создавать `HIGH`.

Отдельно решается, нужно ли для расследования хранить исходную строку через
`logrt[]`. Сырой LOG item не добавляется автоматически вместе с триггером.

Отдельный коммит:

```text
Alert on audit anomalies
```

## Этап 6. Мандатный контроль доступа

### Шаг 6.1. Изучить реальные события отказа

До изменения шаблона проверяются реальные записи Astra Linux SE. Базовый
кандидат:

```regex
type=(AVC|USER_AVC).*denied
```

Этот фильтр нельзя внедрять без проверки: PARSEC может использовать другие поля
и формулировки, чем SELinux.

Изменение шаблона: отсутствует.

### Шаг 6.2. Добавить один счетчик подтвержденных отказов

Добавляется только item с регулярным выражением, проверенным на примерах.

Отдельный коммит:

```text
Collect mandatory access denials
```

### Шаг 6.3. Добавить HIGH-триггер

Severity и условия согласовываются после оценки фоновых отказов. Если штатные
приложения регулярно создают отказ, сначала уточняется фильтр, а не повышается
порог без анализа.

Отдельный коммит:

```text
Alert on mandatory access denials
```

## Этап 7. PARSEC-аудит

Этот этап выполняется только для Astra Linux SE после проверки активных правил
PARSEC.

### Шаг 7.1. Измерить поток parsec-f без Zabbix

Нужно оценить количество событий за типичный рабочий день и понять, какие
операции и объекты в них содержатся.

Изменение шаблона: отсутствует.

### Шаг 7.2. Добавить счетчик parsec-f

Фильтр:

```regex
key="parsec-f"
```

Добавляется только числовой `logrt.count[]` item без trigger.

Отдельный коммит:

```text
Add PARSEC file audit counter
```

### Шаг 7.3. Измерить и добавить счетчик parsec-p

После отдельной оценки потока добавляется второй item:

```regex
key="parsec-p"
```

Отдельный коммит:

```text
Add PARSEC process audit counter
```

### Шаг 7.4. Определить полезные PARSEC-оповещения

Общий объем `parsec-f` и `parsec-p` сам по себе не всегда означает атаку.
Триггеры добавляются только после выявления конкретных опасных операций,
результатов или защищаемых объектов.

Каждая новая операция или категория добавляется отдельной итерацией.

## Этап 8. Выборочное хранение сырых строк

Только после стабилизации счетчиков рассматриваются `logrt[]` items типа `LOG`.

Приоритетные кандидаты:

```text
DAEMON_ABORT и DAEMON_ERR
RESP_*
ANOM_* и INTEGRITY_*
критичные изменения security-конфигурации
подтвержденные отказы мандатного доступа
```

Для каждого кандидата отдельно согласовываются:

- необходимость хранения полной строки;
- риск попадания чувствительных данных;
- срок истории;
- объем данных;
- права пользователей Zabbix на просмотр;
- необходимость отправки события во внешнюю SIEM.

Один новый raw log item — одна итерация и один коммит.

## Этап 9. Техническое укрепление

Технические улучшения выполняются отдельно от добавления новых security-фильтров.

### Шаг 9.1. Валидация экспорта

Добавить автоматическую проверку:

- YAML;
- UUIDv4;
- уникальности UUID;
- уникальности item keys;
- ссылок trigger expressions на существующие items.

### Шаг 9.2. Макросы

После появления проверенных порогов вынести в макросы:

```text
порог неудачной аутентификации WARNING
порог неудачной аутентификации HIGH
окно подсчета
срок хранения сырых строк, если применимо
```

Каждая группа связанных макросов добавляется вместе только с тем trigger, для
которого она нужна.

### Шаг 9.3. Теги

Для audit items использовать:

```text
scope=security
component=audit
control=event
```

Для PARSEC:

```text
scope=security
component=parsec
control=event
```

Новые значения тегов сначала документируются, затем добавляются отдельным
изменением, если затрагивают уже существующие объекты.

## Что сознательно откладывается

До завершения базовых этапов не следует добавлять:

- сбор всех `EXECVE`;
- сбор всех `USER` или `LOGIN` строк широким фильтром;
- полное копирование предустановленных XML-шаблонов;
- хранение всего audit.log в Zabbix;
- сложную корреляцию многострочных audit-событий;
- большое количество PARSEC-триггеров без измерения потока;
- массовую переработку структуры текущего шаблона.

## Ближайшая точка принятия решения

До первой правки шаблона нужно выполнить этап 0 и согласовать:

1. Читает ли `zabbix-agent2` audit.log.
2. Как называются ротированные файлы.
3. Есть ли обезличенный пример неудачной аутентификации.
4. Создаем ли отдельный `Template Astra Linux Audit` или временно расширяем
   `Template Astra Linux Basic`.

После этого первой атомарной доработкой должен стать только item
`Audit: failed authentication events count`, без trigger.
